# 会话与工作树延迟排查

2026-10-22，基于 `d1ca8d2` 排查浏览器、控制面板服务端和本地 Agent。这里的测量均为本机微基准，不包含公网或模型响应延迟，也不代表生产环境端到端耗时。

## 本次优化

| 环节 | 原有开销 | 调整 |
| --- | --- | --- |
| 项目／工作树创建 | 创建后刷新模型目录、全主机会话及历史，必要的目录活动核验与无关同步串在一起 | 保留目标项目活动核验，分离无关模型、用量及历史读取 |
| 工作树预检与概览 | 多次独立 Git 查询串行启动 | 并行执行只读查询，全部校验通过后再修改仓库 |
| 发送／接管任务 | 忙碌检查遍历每个会话时复制整个主机状态 | 一次读取状态，并按目录预计算项目集合 |
| 执行前工作区快照 | 文件的路径核验、打开、读取、关闭逐个串行执行 | 每批最多 16 个文件并行，保持稳定顺序及原有文件数、单文件和总字节限额 |
| 会话摘要 | 查询最近结束时间时扫描会话所有事件 | 仅终止事件的部分索引，按时间取第一条；数据库版本升至 71 |
| 提交与创建反馈 | 操作已经受理／创建成功，界面仍等待概览和历史请求 | 按操作回执结束等待，数据刷新在后台继续；执行状态仍以主机回执为准 |
| 创建会话选项目 | 等全部分页完成后显示项目 | 先展示已有项目，再逐页补齐 |
| 长会话输入 | 输入和回执更新时重复排序、合并全部历史 | 按事件数组缓存历史投影 |
| 工作树完成检测 | 首次固定等待 800 ms，之后再次搜索新项目 | 150、300、600、800 ms 退避轮询；优先使用服务端校验后的项目 ID |

## 测量与验证方法

- 工作区快照：在本仓库、同一主机、相同内容上交替运行修改前后实现各 10 次。896 个列举文件，852 个可采样文件；中位数约 **390 → 120 ms**，减少约 **七成**。仓库触及采样限制，两版可采样集合一致。此项位于每轮任务实际执行之前。
- 最近结束时间查询：内存 SQLite 中构造 50,000 条事件，其中 50 条终止事件，预热后各执行 100 次；单条查询中位数 **27.55 → 0.0011 ms**。这个数字仅描述索引查询，不应换算成整个会话页面的加速倍数。
- Git 工作树：临时仓库、100 个跟踪文件、关闭环境初始化，各 10 次有效采样，创建中位数 **69 → 55 ms**，4 个工作树概览 **297 → 268 ms**。共享主机波动较大，这组结果只用于确认方向。
- 回归覆盖：新项目首条任务、外部活跃任务阻止冲突、运行环境切换、无关历史读取卡住、提交后刷新卡住、旧版项目 ID 回退、轮询截止时间、迁移已有事件库、事件乱序、文件采样上限、符号链接及 Git 索引保持。

最终验证：控制面板服务端 414 项通过，本地 Agent 616 项通过、11 项按平台／原生环境条件跳过，前端相关测试 132 项通过；TypeScript 构建／检查及补丁空白检查通过。

## 后续优先项

1. **批量构建会话列表。** 空历史、空用量的隔离样例中，单会话摘要仍执行 24 次数据库调用，20 条会话列表执行 482 次。主要是逐条读取主机元信息、计算用量和检查目录锁。适合做请求内批量读取；租约、权限和任务状态需要保持实时校验。
2. **按事件范围刷新界面。** 当前持久事件约每 120 ms 合并触发概览与详情刷新，概览时间变化又会触发项目目录和已展开会话列表刷新。按事件涉及的主机／项目／会话更新可减少请求和重复渲染。
3. **降低后台发现成本。** 全量发现仍逐会话读取原生 cwd／用量，多次复制状态；可按目录合并解析、批量读取元数据，并减少完整状态副本。
4. **分段观察原生运行环境启动。** 新建 writer、恢复会话、历史导入、Git 检出和用户环境初始化脚本仍有真实工作量。进一步优化前应分别记录这些阶段的耗时，避免用更快的界面反馈掩盖实际执行等待。

发布时必须遵循 `release-provenance.md`。数据库迁移首次建立索引会读取现有事件；本地 Agent 的优化需要对应 Agent 版本更新，单独更新网页不会使主机执行逻辑生效。

## 2026-10-26：PostgreSQL 迁移后的列表等待

线上基线为 `e5581c1`，实际后端已切换到 PostgreSQL；终止事件索引仍存在。只读连接的简单查询约 0.2–0.7 ms，不能解释秒级停顿。十分钟请求日志显示：

| 路由 | 样本数 | 中位数 | P95 |
| --- | ---: | ---: | ---: |
| `/api/dashboard` | 59 | 9,020.5 ms | 12,908.1 ms |
| `/api/projects` | 132 | 7.6 ms | 11.5 ms |
| `/api/sessions`（混合分页参数） | 227 | 37.9 ms | 561.8 ms |
| `/api/sessions/:id` | 95 | 48.1 ms | 68.8 ms |
| `/api/sessions/:id/events` | 87 | 69.7 ms | 155.8 ms |

根因是 `RegistryService.dashboard()` 为统计数量而调用未批处理的 `listSessions()`，然后才取最近 20 条和受管／活跃会话。线上 532 条可见会话全部执行详情、用量、租约和权限计算。PostgreSQL 同步适配层逐次等待数据库，阻塞 Node 主线程；其他请求也会排队。迁移新增的分页批处理没有覆盖这条仪表盘路径。前端又等待仪表盘和列表一起完成，刷新频率进一步放大了等待。

修复先读取轻量目录元信息用于统计，仅为最近 20 条及所有受管／运行／待审批会话生成完整摘要。分页、兼容的全量列表和仪表盘复用同一请求内批处理方法；重叠会话只读取一次。权限、租约和用量计算仍使用原服务逻辑，不使用跨请求缓存，也不截断较早的活跃会话。

在迁移演练的独立 PostgreSQL 数据库上，用相同账号、数据和数据库连接配置各调用仪表盘 5 次，结果如下。副本包含 503 条可见会话、45 条活动展示会话；这是服务方法耗时，不含 HTTP、浏览器和公网时间。

| 项目 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 中位耗时 | 12,956.9 ms | 415.5 ms |
| 每次完整摘要数 | 503 | 62 |
| 每次数据库驱动调用数（含批量调用） | 13,094 | 248 |

修复前后仪表盘完整返回对象逐字段一致。回归测试要求总数仍包含历史记录、较早的受管／运行／待审批会话仍出现、结束时间不丢失、返回摘要与单条读取一致，并限制详情读取仅发生于实际返回会话。

控制面板服务端全量回归：PostgreSQL 430 项全部通过；SQLite 427 项通过、3 项 PostgreSQL 专用测试跳过。TypeScript 构建及补丁空白检查通过。

同步数据库适配层仍然阻塞主线程；高频全局刷新和其他长查询仍是后续优化项。本次修改无需数据库迁移或主机 Agent 升级。
