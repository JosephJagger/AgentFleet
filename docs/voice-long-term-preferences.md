# Explicit long-term voice preferences

AgentFleets stores explicit personal voice preferences independently of tasks, job results, and conversation history. Settings → Long-term preferences supports viewing, adding, editing, disabling, expiring and deleting records (five per page). Global voice can manage the same records through `agentfleets_panel` preference tools; ordinary session voice uses the saved rules but directs management to Settings. Nothing automatically learns from history or dispatches work.

## Native capability decision

The host uses Codex App Server, stdio JSON-RPC, not an assumed web/SSE memory service. Experimental JSON schemas generated from actual Codex 0.160.1 and 0.161.0 contain `memory/status` (`v2Ready`, `v2ConsolidatedThreads`), `thread/memoryMode/set`, and `memory/reset`. They do not expose per-preference CRUD. Fresh isolated App Server probes accepted the memory status query and an ephemeral thread with memory generation/use disabled; no turn was started. Native asynchronous host-local memories are not an authoritative cross-host preference database. See [Codex memories](https://learn.chatgpt.com/docs/customization/memories?surface=app).

The chosen backend therefore owns structured rules and sends them through actual native `thread/realtime/start.prompt`. The experimental realtime v3 API also accepts `thread/realtime/appendText` with `role: developer` for live snapshot updates. This is an instruction channel, not a native memory CRUD API. Startup history context is disabled so old transcripts are not used to reconstruct deleted preferences. The ephemeral global coordinator disables native memory generation and use for its own thread only; host-global settings are untouched.

## Storage and bounds

Migration 54 adds per-workspace/per-user preferences, revisions and idempotency metadata. All reads/writes bind authenticated workspace and user; web writes require existing CSRF protection, voice tools require call ownership. Rules preserve body, conditions, enabled state and optional expiry. Updates use revision checks; exact duplicate creates reuse a record. Deleted records lose body and conditions, retaining only tombstones and request metadata to reject stale save retries. Audit records contain identifiers/revisions, never rule content. Existing infrastructure backups retain their normal retention policy; this feature does not purge historical backups.

No automatic summarization or semantic compression occurs. Each rule has a 2 KiB UTF-8 body/conditions limit. At most 50 effective rules fit in an 8 KiB complete JSON snapshot, including metadata; at most 200 undeleted records including disabled/expired rules. Over-limit writes roll back and ask the user to organize records; no silent truncation. Voice management lists three records per page with revision-bound cursors and bounded mutation receipts. Active rules are loaded in full, so conditional English rules are not dependent on a retrieval guess. The model is instructed to list existing rules and update a conflict, asking when ambiguous; semantic conflict detection remains model-mediated, not a guaranteed NLP constraint. Editing a known record is deterministic.

## Call lifecycle and limitations

Agent 0.30.90 or newer is required to apply saved preferences. Old/unknown agents never receive preference update messages; an explicit per-call opt-out permits a call without preferences. A new call or reconnect reads a fresh authoritative snapshot, and the UI reports host acknowledgement. Existing calls poll via their 15-second heartbeat. Additions send a full snapshot; read/update failures leave audio connected. Changes, deletion, disabling and expiry request a reconnect because native append-text cannot erase already supplied context. No automatic hangup or forced reload occurs. Reconnect is required to physically clear old voice context; a running call cannot offer immediate erasure guarantees.

Rules apply to global and session voice responses, not text task workers or standalone native clients. They do not authorize execution. Speech recognition and model adherence remain probabilistic. The English-correction acceptance fixture verifies intact prompt delivery and conditions, but actual microphone/audio behavior needs live acceptance. An unclear transcript should produce a request for the original wording, never a guessed correction.

Tests cover persistence across database reopen, user/workspace isolation, CSRF, duplicate and stale retries, deletion without resurrection, replacement, expiry, capacity rollback, bounded tool pagination, native prompt/update transport without starting a task, update receipts and browser call continuity. Release uses the voice-safe publisher; active calls defer cutover. Host upgrades use existing idle/maintenance protection.
