# 跨领域输入辅助与对话经验库

状态：项目设计与现状核对。本文中的目标、数据结构和阶段待办均为待实现设计，不代表已上线能力。

## 1. 产品目标

帮助用户把想做的事说清楚，支持专业人员的术语输入，也支持非专业人员的日常表达。默认使用本地词库、自建后端 NLP 和经确认的个人/项目经验，不要求配置外部模型。中英文是同一套概念的两种表达，不以界面语言限制输入语言。

项目由三个产品模块组成：

| 模块 | 用户价值 | 主要输入 | 输出 |
| --- | --- | --- | --- |
| 术语匹配 | 想得起意思但想不起术语，或减少重复输入 | 前缀、简称、别名、口语、项目术语 | 标准术语、简短解释、领域与出处 |
| 表达优化 | 将模糊需求变为明确、保留约束的请求 | 当前草稿、选定领域、确认的术语 | 可编辑的改写、可选补充项，或需要澄清的歧义 |
| 对话历史学习 | 复用自己的提问经验和已验证方法 | 用户问题、Codex 回复、后续纠正、采用反馈 | 可追溯的历史案例、个人表达偏好、待确认词条 |

历史模块内部必须分开保存“用户问”和“Codex 答”，再关联为一次交互；不能把两者混成词频统计，也不能把模型回答自动视为事实。

## 2. 当前系统的真实能力

基线：截至 `68e9d25`，数据库 schema 29。

| 能力 | 当前情况 |
| --- | --- |
| 用户/助手角色 | 收到的消息正文以 `userMessage`、`agentMessage` 等 item 类型区分 |
| 消息历史 | `durable_events` 保存事件和会话标识，`content_blobs` 保存允许同步的正文，并受保留期限及删除策略约束 |
| 配对线索 | 有 `logical_session_id`、`execution_segment_id`、可空的 `native_thread_id`、`native_turn_id`、`native_item_id`，以及事件顺序 |
| 自动提取 | 新收到并持久化的用户或助手完成消息可分别提取反引号术语和明确引号释义 |
| 学习词库 | `writing_memory` 保存短语、替换表达、个人/项目范围、来源事件/会话、候选或确认状态、采用次数 |
| 学习开关 | `writing_learning` 保存用户/会话开关、范围和处理水位；关闭期间不会补学 |
| 基础词典 | 3,943 条过滤后的 CSpell 软件词汇，另有小规模手工中英文词条和固定表达规则；单词数不等于语义概念数 |
| 后端 NLP | ICU 中文分词、同义词与组合条件，覆盖 10 类软件开发场景；目前不使用历史问答或语义向量 |
| 采用反馈 | 确认词条的点击采用有计数；尚无通用的“曝光—采用—编辑—发送—有用/无用”反馈链 |
| 完整问答经验库 | **未实现**；没有独立的问答配对、回答用途、结果验证、纠错和历史案例检索模块 |
| 无限制历史学习 | **没有**；未同步、已过期或删除的正文不可补出，现有学习也不会扫描所有旧记录 |

记录机制的代码入口：`apps/control-plane/src/db.ts`、`server.ts` 的 `event.append` 分支、`writing-memory.ts`。不能仅按消息“相邻”推定问答关系，不能保证每个历史事件都带有完整的轮次标识。

## 3. 领域与场景目录

默认自动建议领域，允许用户在会话或项目中固定领域。以下是首批设计范围；“工程”先覆盖通用工程表达和常见工程工具，不假定用户只指软件工程。

| 领域 | 子场景 | 术语示例 | 口语需求示例 |
| --- | --- | --- | --- |
| 编程开发 | 前后端、数据库、测试、部署、性能、界面、数据处理 | 防抖、幂等、回归测试、数据库迁移、缓存失效、响应式布局 | “点两次生成了两笔订单” |
| 工程 | 需求与规格、设计图纸、机械与制造、土木/BIM、电气、仿真、质量与项目交付 | 公差、尺寸链、物料清单、版本基线、设计评审、有限元、碰撞检查 | “这几个零件装不到一起，尺寸要核对” |
| 游戏 | 玩法逻辑、引擎脚本、关卡、角色动画、物理、联机、资源与性能 | 状态机、碰撞体、寻路网格、对象池、动画混合、客户端预测 | “角色跑到墙角会卡住” |
| 视频剪辑 | 素材管理、剪辑、字幕、音频、调色、特效、导出与批处理 | 时间线、关键帧、代理媒体、帧率、码率、音画同步、响度、色彩空间 | “声音比嘴型慢一点” |
| Agent 使用 | 任务拆解、工具调用、技能/MCP、上下文、检查点、人工确认、失败恢复、多步骤协作 | 工具调用、上下文窗口、结构化输出、重试、幂等执行、人工介入 | “做一半断了，接着做但别重复跑” |
| 办公自动化 | 表格、文档、演示、邮件与日历、文件整理、报表、审批、OCR、系统间同步 | 数据透视表、字段映射、去重、邮件合并、定时任务、增量同步、批量重命名 | “把每个月的 Excel 合起来，重复的只留一份” |

同词跨领域必须拆分义项，例如“渲染”在网页、游戏和视频中的任务不同，“代理”可能指代理媒体、网络代理或 Agent。没有足够上下文时展示可选解释，不能直接选择一个技术方案。

每个领域都需要四种材料：规范术语、真实口语变体、任务模板、误匹配反例。保留混合语言和产品名，例如“把 Excel 按客户汇总”“Unity 角色会穿墙”。

## 4. 语料结构与质量

### 4.1 概念词条

建议结构：

```text
concept_id              稳定标识，独立于展示文字
domain / subdomain      领域和子领域
sense_id                多义词义项
labels.zh / labels.en   中英文规范名称
aliases.zh / aliases.en 别名、缩写、常见错字与口语
definition.zh / .en     简短定义
positive_examples       应当命中的上下文
negative_examples       不应命中的相似表达
related_concepts        相关、上位、下位或易混淆概念
scope                   基础库 / 当前用户 / 当前项目
sources                 来源、版本、授权方式与引用位置
review_status           草稿 / 待核对 / 已审核 / 已废弃
introduced_version      首次发布的语料版本
```

不要用中文解释英文词条冒充“中文覆盖”。同一个概念的大小写、复数和别名不重复算概念数。基础软件拼写词表保留为单独资源，不与审核过的概念库混报数量。

### 4.2 表达优化场景

```text
intent_id / domain      场景与领域
goal                    用户目标
objects                 操作对象
symptoms                已描述的现象
constraints             必须保留的时间、范围、单位、工具及禁止事项
slots                   用户可补充的信息，不强制填写
rewrite_templates       中英文改写模板
clarification_options   多义或缺少关键信息时的澄清选项
positive / negative     正例与反例
evidence_requirements   哪些结论必须先有证据
```

优化器先区分用户在“描述问题、要求实现、咨询概念、下达限制”中的哪一种。用户描述现象时不擅自补成已确定的原因；用户没指定软件、引擎、算法、规格或收件人时，不自行填入。数值、单位、否定词和已有工具选择必须保留。

示例：“把每个月的 Excel 合起来，重复的只留一份”可以建议“合并各月 Excel 数据并去重”，并提供“按哪些字段判断重复”的可选补充，不能直接假定按姓名去重。

### 4.3 语料规模与来源

首个完整多领域版本的设计目标是 **1,200 个已审核双语概念、180 个优化场景**，六个领域各至少 200 个概念、30 个场景。这是目标，不是当前库存。先以每领域 30 个概念、10 个场景做垂直样例，再按漏召回和用户反馈扩充。

每个场景至少准备 6 个正例和 4 个反例，目标评测集至少 1,800 条。评测与开发样例分开保管；改写同一个句子得到的近重复例子不能充当独立测试集。

来源优先级：团队原创审核材料；授权允许再利用的标准术语资源或官方文档中的事实整理；用户明确确认的个人/项目经验。记录来源和许可证，不批量复制闭源文档、付费教程或未知来源问答。首次整理外部来源时再逐项核验版本和许可，本文不宣称任何待选资源已获授权或接入。

语料必须支持数据文件导入、结构校验、别名冲突检查、审核差异、版本发布、回滚和按领域统计；避免继续把词条堆在条件分支里。

## 5. 用户问题与 Codex 答案的记录机制

### 5.1 三层记录

1. **原始消息层**：复用现有事件与正文存储，保留角色、原始文本、顺序、来源与原生标识。原始对话不因建议而改写。
2. **交互关联层**：新增可重建的 interaction 索引，关联一组用户消息与一组助手回复，以及完成、失败、中断等事件。
3. **审核经验层**：从交互中产生术语、问法映射、工作流程或案例摘要候选，确认后进入个人/项目检索。

“一问一答”是展示形式，不应是数据库限制。同一轮可能有追加问题、多条中间回复和最终答复；重试、分支、恢复会话和补录历史也可能产生重复或缺项。

建议新增的数据实体：

| 实体 | 核心字段 |
| --- | --- |
| interaction | workspace、session、execution segment、native thread/turn、状态、关联可靠性、领域、时间、水位 |
| interaction_message | interaction、event/item 标识、role、顺序、正文引用、正文可用状态、可知时的提交者标识 |
| suggestion_event | suggestion_id、概念/场景/语料版本、用户、会话、曝光/采用/编辑后发送/关闭/有用/无用、时间 |
| experience_candidate | 来源 interaction/event、概念或意图、候选摘要、作用范围、审核状态、后续纠正关联 |
| experience_evidence | 用户确认、相关可验证结果、被否定的原因、关联事件标识；不把助手自称成功当验证 |

原生导入的用户消息不一定能识别为哪个登录账号提交，字段必须允许未知。经验的拥有者与原始消息作者分别建模，不能把工作区内所有原生用户消息归到当前查看者名下。

### 5.2 关联规则

- 优先以工作区、会话、执行段、原生 thread/turn 标识关联；使用 item/event 标识去重。
- 同一 item 的 started/completed/更新是同一消息的状态演进，不当成不同问答。
- 一轮内追加的用户消息与多个助手消息按顺序保存；不强行逐条一对一匹配。
- 缺少标识的历史仅记录“未可靠关联”，不凭时间相邻自动晋升为训练材料。
- `turn.completed` 只代表执行结束，不代表答案正确或满足需求；failed/interrupted 单独记录，未回答的问题保留未回答状态。
- 用户后续“不是这个意思”“这样不对”可以形成纠正候选，但不只靠关键词自动判定事实正误。
- 工具输出、运行日志和内部推理不当成 Codex 最终答案。工具结果只能在明确需要时引用为证据。

### 5.3 学习路径

```text
用户原话 → Codex 回复 → 可靠的交互关联
                         ↓
              提取术语/意图/流程候选
                         ↓
                去重、领域识别、审核
                         ↓
                个人或项目经验库
                         ↓
           下次输入时检索，并显示来源
                         ↓
           采用、改写、发送、有用/无用反馈
```

“用户点了采用”说明表达可能有帮助，不等于答案正确；“发送了采用后的草稿”比单击更能说明意图；“用户确认解决”与验证证据又是另一层信号。必须分开统计。

历史检索默认只使用当前用户有权限的个人/项目范围，不因为同属某个领域而跨用户共享。公共基础语料只有独立审核发布后才能更新。这里的学习首先是检索与排名改善，不是自动微调模型。

### 5.4 保留、关闭和删除

- 未发送草稿不进入问答经验库。后端 NLP 的临时请求不作为用户问题记录。
- 原始正文继续遵循项目同步和保留策略，不为了学习静默延长存储期限。
- 候选引用失效的原文时标记不可用并停止基于该原文的检索；索引、缓存和未来向量库需要同步失效。
- 用户确认独立保存的经验应明确展示其独立保留属性，并支持“删除原对话时同时删除衍生经验”。不能默认把历史删掉但仍保留可还原的摘要。
- 自动学习、历史建议、后端表达建议和术语补全分别可关闭。关闭学习不改变现有已确认词条；关闭历史建议不停止原本授权的消息历史同步。
- 旧历史回填是单独作业：说明范围，支持暂停、水位和幂等重跑；不将这次项目设计视为授权无限回扫全部主机历史。

## 6. 匹配与交互架构

检索顺序：即时术语 → 停顿后的领域/意图匹配 → 有权限的历史经验 → 可选的自建语义向量召回 → 可选外部 AI 理解。后两项只有实现并验证后才启用。

术语匹配用别名、前缀和拼写容错；表达优化使用分词、短语、对象/目标/约束槽位；历史建议优先匹配当前项目和已确认案例。领域置信度低时保守提供候选，不直接替换草稿。

未来语义向量只负责召回相近案例，仍需词面约束、多义消歧和证据过滤。先评测候选嵌入模型的中英文、领域差异、内存和延迟，再决定运行方式；不把向量相似度称为答案正确率。

用户可辨别三类候选：“术语”“表达优化”“历史经验”。历史经验可以查看问题、回答、纠正、采用状态和来源时间。默认只替换草稿，不发送任务、不执行工具。

保留已确定的交互约束：

- 即时结果不等待后端；后端请求停顿 600ms 后发起，2.5 秒超时并降级。
- 新建议追加，不替换正在键盘选中的已有候选。
- 桌面使用浮层，候选出现/消失不移动输入框。
- 手机术语横滑；表达建议按实际高度、最多四行并省略；收起键盘保留候选。
- 切换会话、账号、修改草稿、关闭建议或输入法合成时，旧结果不能错贴到新草稿。

## 7. 实施阶段与验收

| 阶段 | 交付物 | 验收边界 |
| --- | --- | --- |
| P0 项目基线 | 本文、能力盘点、领域与记录结构 | 已完成设计；不宣称新增语料或问答学习已上线 |
| P1 语料工程与六领域样例 | 数据化词条/意图格式、校验/版本工具、每领域 30 概念与 10 场景、正反例 | 180 概念与 60 场景经审核；全部领域有中文、英文、混合输入及歧义反例 |
| P2 问答关联 | interaction 索引、角色分离、轮次配对、重放去重、未配对状态、来源查看 | 不丢失追加消息，不跨会话/执行段误配，缺标识不冒充可靠配对 |
| P3 历史经验与反馈 | 提取候选、确认/纠正/删除、历史建议、采用后编辑/发送反馈 | 用户可追溯和关闭；旧回复不会自动变成正确知识；删除链测试通过 |
| P4 扩充并评测 | 1,200 双语概念、180 场景、独立评测集、领域覆盖报告 | 按领域报告质量与不足，不能靠大量英文拼写词稀释中文错误率 |
| P5 自建语义召回 | 嵌入模型对比、领域/权限过滤、向量重建与删除、资源预算 | 相比词面基线有可复现收益；误建议和资源消耗不过线；可降级/回滚 |

每阶段分别提交、测试和发布。P1/P2 优先，先把语料和可靠记录做好，再引入更复杂的模型。

质量目标（待测量目标，不是现有成绩）：

- 人工标注的高置信术语候选 top-3 命中率至少 95%；按领域和语言分开统计。
- 高置信表达建议准确率至少 95%；否定、单位、数值和工具约束反例不允许擅改。
- 学习配对确定性测试中，不允许跨会话误配或将工具输出当最终答案。
- 相同草稿因候选出现/消失造成的桌面输入框位移为 0；手机键盘状态有浏览器模拟与真机验收。
- 即时匹配 p95 小于 30ms；本地 NLP 处理 p95 小于 100ms，网络与防抖时间单独报告，并注明硬件和语料规模。
- 未命中率、误建议率、采用后撤销率、领域纠正率、未可靠配对比例、来源不可用比例都应可测；不能只展示总词条数和点击量。

## 8. 需要持续维护的项目资产

领域目录、双语概念库、意图/约束模板、独立评测集、语料来源与授权清单、问答配对样本、版本变更记录、已知不足、发布验收记录。每次新领域或学习策略上线都更新这些资产。

本阶段只建立项目设计。多领域语料、交互关联表、问答经验提取和语义向量检索仍是待实现内容。
